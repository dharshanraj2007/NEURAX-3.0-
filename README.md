# Visual Inspection & Defect Root-Cause Assistant

A software-only industrial decision-support system for the NeuraX Hackathon 3.0
Domain 2 problem statement. It turns the organizer-provided Discrete-Event
Simulation (DES) data and a real public defect-image dataset into one
continuously-updated view of **quality, process-flow health, and
profitability** - with every number traceable back to a real dataset, a real
trained model, or a clearly labeled assumption.

---

## 1. Problem understanding

The problem statement asks for a **unified** system, not three separate
tools: it must (a) classify/localize defects and flag uncertainty instead of
guessing, (b) identify bottlenecks and quantify their effect on throughput
and losses, (c) predict profitability, and (d) tie all of it together with
evidence-based, advisory-only recommendations.

**The critical, easy-to-miss fact about the organizer's dataset:** the
`Manufacturing Data Shared Facility` package is **pure Discrete-Event
Simulation process telemetry** - three Rockwell Arena models
(`Model 1`, `Model 2`, `Model 3`) with utilization, queue, cycle-time and
SKU-routing data. It contains **no images, no defect labels, and no
per-unit inspection outcome** anywhere:

| File | What it actually is |
|---|---|
| `Model 1` / `Model 2` | Design-of-Experiments sweeps: `Demand` varied 1-20, ~150-180 real Arena replications per level (3,000 rows each). A 3-station line (Drilling -> Milling -> Assembly). |
| `Model 3` | **Not a time series.** `Time_Now` is constant (24) on every one of the 605,620 rows - each row is one independent 24-hour production-day replication ("batch") of a 5-stage line (Blanking -> 4 parallel Presses -> 4 shared Assembly Cells -> 2 Paint conveyors -> Quality check), with 77 columns of utilization/queue/SKU-routing telemetry. |
| `3000Samplesv3.mat` | Same kind of simulated output, MATLAB format. |

There **is** a Quality-check station in the process model - but its pass/fail
outcome was never logged as data. This is a deliberate scope decision by the
organizers (a DES facility, not a vision benchmark), not an oversight on our
part, and it means any team claiming "real, measured" defect-to-process
correlation from this package alone would be lying. We treat that gap as a
design constraint to solve honestly rather than paper over:

- **Vision** is trained on a real, independently-sourced, licensed dataset
  (NEU steel surface-defect images - see §3), not synthesized.
- **Process/bottleneck/economics analysis** runs entirely on the real,
  unmodified organizer data - no vision dependency at all.
- **The one link the organizer data cannot supply** (which defect a given
  process condition produced) is generated by a **documented, parameterized
  simulation**, not asserted as measured fact - every constant governing it
  is a named variable in `backend/app/services/defect_link_sim.py`, and the
  system exposes its own methodology at `GET /api/methodology` and on the
  dashboard's Methodology page so nobody has to take our word for it.

### Why this shape

- **Vision and process-mining are independent and each fully real** - the
  system doesn't need a fake link to be useful; the bottleneck/drift/
  profitability half works entirely off real data with zero vision
  involvement, and is demoable even before the detector finishes training.
- **The correlation layer is the one place synthesis happens**, and it is
  isolated into a single, short, heavily-commented module
  (`defect_link_sim.py`) rather than spread invisibly through the codebase,
  specifically so it can be read, questioned, and audited in under two
  minutes.
- **Every "ML choice" is validated against the real data before being
  trusted**, not just implemented and shipped. Two examples encountered
  while building this (kept as comments in the code, not hidden):
  - A first version of the output-driver model put ~100% of its importance
    on the `Quality` station - which turned out to be pure leakage (every
    part passes through Quality/Paint/Blanking exactly once, so their
    utilization is a near-deterministic rescaling of total output, not an
    independent signal). Fixed by excluding single-pass gates from the
    driver-importance regression (kept in the purely descriptive structural
    ranking, where reporting their true utilization is still legitimate).
  - A first version of the defect-class simulator conditioned on each
    station's *raw* utilization level, which barely varies batch-to-batch -
    so a classifier trained on it scored at chance for every class, not just
    the deliberately-uncorrelated `inclusion` one. Fixed by conditioning on
    each station's *standardized anomaly* (z-score vs. its own historical
    mean) instead, which is also the physically correct model (abnormal
    stress causes defects, not ordinary structural load).

## 3. Approach

### Data provenance (see `/api/methodology` for the always-current version)

| Real, unmodified | Documented assumption |
|---|---|
| Model 1/2/3 CSVs, 3,000 + 3,000 + 605,620 rows | Station -> defect-family affinity table (domain-reasoned: press-tooling load -> pitting, blanking/forming stress -> crazing, material handling -> scratches, paint-line issues -> patches; `inclusion` deliberately left uncorrelated as a raw-material-intrinsic defect and a built-in falsifiability check) |
| NEU-DET images + YOLO bounding boxes (Figshare DOI 10.6084/m9.figshare.28903550.v1, CC BY 4.0, md5-verified `19af5a1250d8ab0cb0828d31ee2b349d`) | Unit price / scrap cost / operating cost (organizer data has no $ figures at all - user-editable, defaults are stated assumptions) |
| Trained YOLOv8n weights + isotonic calibration fit on real held-out validation predictions | Partial-dependence "what-if" output sensitivity - a correlational ML association (Model 3 is 605k *independent replications of one fixed capacity design*, not a capacity-sweep experiment, so a precise causal slope can't be rigorously identified from it; labeled as directional intuition, not a guarantee, everywhere it's shown) |

### Tech stack

- **Vision:** PyTorch + Ultralytics YOLOv8n, isotonic-regression confidence
  calibration, raw-confidence "uncertain" flag as an open-set control.
- **Process mining:** pandas/pyarrow (Parquet-cached), scikit-learn
  RandomForest + GradientBoosting, SPC control-chart drift detection.
- **Root-cause:** XGBoost + SHAP, validated with held-out per-class ROC-AUC.
- **Economics:** transparent formula-driven simulator (deliberately *not*
  a black box - the PS asks for advisory, explainable recommendations).
- **Backend:** FastAPI, cached/warmed at startup so the dashboard feels
  instant despite several of these being genuinely-fitted models.
- **Frontend:** React + TypeScript + Vite + Tailwind + Recharts, an
  industrial dark-theme dashboard (deliberately not a generic "AI SaaS
  gradient" look) built to the project's data-visualization palette
  standard (fixed categorical hue order, status colors reserved, real
  hover/tooltip interaction, no dual-axis charts).

### Running it

```bash
# 1. Data + model (one-time, ~1-3h on CPU - no GPU required)
cd ml
python prepare_dataset.py     # real, stratified 80/20 split of NEU-DET
python train_detector.py      # fine-tunes YOLOv8n
python calibrate.py           # isotonic calibration on real held-out val images

# 2. Backend
cd backend
uvicorn app.main:app --reload   # http://localhost:8000

# 3. Frontend
cd frontend
npm install
npm run dev                     # http://localhost:5173
```

### What each checkpoint should look at

- **Checkpoint 2 (partial execution):** the process-mining + economics
  layers are fully functional immediately (no training required); the
  vision layer becomes live once `ml/train_detector.py` finishes.
- **Checkpoint 3:** see the Methodology page in the dashboard, and the
  `caveat`/`note` fields returned by `/api/process/bottleneck` and
  `/api/root-cause` - these are the same honesty-first disclosures a judge
  would want to see, surfaced in the product itself rather than only in
  this document.
